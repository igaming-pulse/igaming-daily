這個任務**在半夜由排程自動執行，沒有任何人在看**。

- **嚴禁反問、嚴禁徵詢確認、嚴禁停下來等指示。** 你問了也沒有人會回答，
  整個任務就在那裡空轉到結束，當天的日報等於沒產出。
- 遇到模稜兩可、看起來需要確認的情況：**選最合理的解讀，直接做下去**，
  然後在最後的回報裡寫一段「本次的判斷與假設」說明你怎麼決定的。
- 只有在「做下去會造成不可逆的破壞」時才可以中止 —— 下面列的狀況**都不屬於**這一類。

### 已經預先裁示的狀況（不要再為這些問問題）

1. **當天的報告已經存在** → 照樣重跑並**覆蓋**它。這是預期行為，不是異常。
   ⛔ **絕對不可以把 `reports/<今天日期>.html` 拿來當「已經報導過」的依據做去重。**
   那一份是**要被取代的舊版**（別台機器或前一次執行留下的），它不是歷史，是待覆蓋物。
   去重只能比對**日期早於今天**的日報檔。
2. **目前分支不是 main** → 正常。併行期就是跑在 `test-publish` 上。
3. **推送目標** → 一律 `git push` 推**當前分支**。
   ⛔ **絕對不要切換分支**、不要 checkout main、不要開新分支。
4. **推了不會觸發 Email／Telegram** → 正確且刻意如此。併行期不發通知，
   由舊環境負責發。這不是要修的問題。
5. **收集時間窗與今早那份重疊** → 沒關係。窗一律是「實際執行時刻往前推 24 小時」，
   重疊是正常的，照算就好。

6. **「這則前幾天好像看過」** → 去重的界線只有 SKILL.md 明文寫的那幾條
   （例如 EEZE 近 3 天同議題）。**不要自行擴大**成「這家公司／這個展會前幾天出現過就整則剔除」——
   同一家公司的不同新事件、展會期間的後續發布、年報數字的正式公布，**都算新消息**。
   判不準時的預設動作是**收進來**，在 Telegram 品質備註寫一句「疑似與 X 月 X 日重疊」，
   **而不是剔除**。整份收錄掉到 6 則以下，幾乎一定是去重做過頭了。

## 要做的事

1. 確認你在 repo 根目錄，先執行 `git pull --ff-only`。
2. 完整讀取 `skills/SKILL.md`。
3. 嚴格依照該檔的「執行步驟」章節，**從步驟 0 一路做到步驟 6**，依序完成，
   每一步做完再做下一步。
4. 任何一步失敗就依該檔的「失敗警報」規則處理，並在最後明確說明卡在哪，
   不要假裝成功、也不要因此中止後面還做得到的步驟。

## 硬規則提醒（SKILL.md 內有完整版，以該檔為準）

- 嚴禁平行 sub-agent，全程主線循序
- 交叉查證每則上限 3 次
- 整場 firecrawl ≤ 30 次（輪掃 8 ＋ 其他 ≤ 22）、WebSearch ≤ 60 次
  （WebSearch 不吃 Firecrawl 額度，上限放寬是為了讓你查得夠徹底再下判斷）
- ⛔ 收錄少於 8 則時，**先回頭把預算用滿**再下「今天新聞真的少」的結論 ——
  抓取不足造成的假性偏少，比漏收更嚴重
- 嚴禁開 5-credit 的 JSON 抽取；og:image 跟 summary 同一次帶回
- 每則必附真實可點擊原文 URL，抓不到就不收
- 品質備註只能進 Telegram，不可進日報或 Email
- 收集時間窗 = 實際執行時刻往前推 24 小時（補跑也照這個算，不要回頭用 02:30）

## 完成的定義

這次執行只有在**下面兩件事都成立**時才算成功：

1. `reports/<今天日期>.html` 已經寫好
2. 已經 `git commit` 並 `git push` 成功（commit message 格式 `daily: YYYY-MM-DD report`）

兩件事沒同時做到，就在回報裡明確寫「本次未完成」以及卡在哪一步。
